# Trace Playbook

Detailed procedures for each trace direction. Read this during Step 5 of the
trace skill.

---

## Tracing Upward (toward the entry point)

The goal is to find the path from the selected code back to where a user,
system, or job triggered it.

1. **Find direct callers** — grep for the method name or class instantiation.
   Filter results to calls (not definitions). If results are too broad, narrow
   by adding the class name or module context.

2. **Follow the chain** — for each caller, repeat: find *its* callers. Continue
   until you reach one of these terminal points:
   - A route definition (routes file, URL conf, router)
   - A background job `perform` method called by a queue
   - A webhook or event receiver
   - A console/CLI command or Rake task
   - A test (stop here — don't trace into test callers)

3. **Handle callbacks and hooks** — if the code is a callback (before_action,
   after_commit, observer, lifecycle hook), note the trigger condition and which
   layer owns the hook. Include it as a lateral branch, not the main upward path.

4. **Handle concerns and mixins** — if the method is included via a module or
   concern, identify the including classes. Trace through the most representative
   includer.

---

## Tracing Downward (toward data and dependencies)

The goal is to find what the selected code ultimately reads or writes.

1. **Read the method body** — identify every outbound call: service objects
   instantiated, model methods called, jobs enqueued, external clients invoked,
   cache operations, file I/O.

2. **Follow into the data layer** — for each outbound call, read the called
   code and continue until you reach:
   - An ORM query (`.find`, `.where`, `.save`, `.create`, QuerySet, etc.)
   - A raw SQL call
   - An external API call (HTTP client, SDK method)
   - A cache read/write
   - A file system or storage operation

3. **Note async handoffs** — if the code enqueues a job, publishes an event,
   or broadcasts over a websocket, trace the async path separately and mark it
   with `↓ (async)` in the diagram.

4. **Note external integrations** — if the code calls an external service
   (payment processor, email provider, third-party API), identify the client
   class, the specific method, and what data is sent/received.

---

## Tracing Laterally (cross-cutting concerns)

Look for side effects that fire along the main path but aren't part of the
primary flow:

- **Callbacks** — `after_create`, `before_save`, `after_commit`, signal
  receivers, lifecycle hooks. Note what they do (send email, enqueue job,
  invalidate cache) and when they fire relative to the main flow.
- **Authorization** — identify where access control is enforced (policy check,
  middleware, before_action). Note what happens on failure.
- **Audit/logging** — note any structured logging, audit trail writes, or
  analytics events that fire along the path.
- **Instrumentation** — ActiveSupport::Notifications, StatsD calls, Sentry
  breadcrumbs, or similar observability hooks.
- **Pub/sub or events** — domain events published, subscribers that react, or
  websocket broadcasts triggered.

---

## Handling Common Complexity

**Deep inheritance chains** — if the method is defined on a base class or
concern, note the inheritance path briefly (e.g. `InvoicesController < ApplicationController`). Don't trace into the full base class unless it's directly relevant.

**Polymorphism** — if the code dispatches to different implementations based on
type, note the polymorphism point and trace the most common or interesting path.
Flag the others.

**God objects / large models** — if tracing hits a model with many callbacks
and associations, be selective. Trace only what's relevant to the input code.

**Missing code** — if a called method can't be found via grep (e.g. it's
dynamically defined, generated by a macro, or in a gem), say so explicitly.
Identify the macro or gem responsible and note what it likely produces.

---

## When the Trace Is Ambiguous

If the input code could belong to multiple flows (e.g. a shared service called
from many entry points), ask the user which context they care about:

> "This service is called from several places — invoice creation, subscription
> renewal, and the admin panel. Which flow should I trace?"

If the user doesn't specify, trace the most common or most interesting path and
note the others briefly.
